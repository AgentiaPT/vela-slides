# Sprint "Trim" — Part-File Right-Sizing for Coding Agents

**Date:** 2026-08-08 · **Codename:** trim · **Base branch:** `main`

## Context

Vela's source part-files have grown past the point where a coding agent can read
them. Measured empirically against these exact files, not estimated.

**Agent read limits (observed):**
- `Read` caps at **25,000 tokens** per call
- `Read` refuses any file over **256 KB** outright

**Measured token density: ~2.35 chars/token for JSX, ~2.5 for Python** — not the
usual ~4. Vela's inline-style JSX (`style={{ fontFamily: FONT.mono, fontSize: 9, … }}`)
is punctuation-dense; the Python is comment- and f-string-heavy. Byte size
underestimates token cost by ~1.7×. Five files were measured directly by the harness;
the rest are derived from those ratios.

### Why it matters

**Time / cost per sprint.** The three highest-churn parts are all over the cap:
`part-imports.jsx` (25 of the last 120 commits), `part-uitest.jsx` (17),
`part-slides.jsx` (11). Every sprint touching them pays a pagination tax — 3–4
sequential `Read` calls (77K tokens for one file, re-read on every context reset) or
grep-blind editing. `part-pdf.jsx` is reachable only via `sed`/`grep`, which is why it
is effectively frozen (1 commit in 120). `tests/test_vela.py` is the mandatory
after-every-change file, so its 70K is billed every sprint regardless of what changed.

**Quality.** A truncated read returns a partial view plus a "do not answer from this
page alone" warning. Editing from a partial view produces the documented failure
modes: modifying the wrong function, missing callers, re-implementing something
further down the file. `concat.py` already fails the build on duplicate top-level
declarations — a guard that exists because that risk is real here.

**Security.** The deck-sanitization surface (`sanitizeSvgMarkup`, `sanitizeStyle`,
`sanitizeUrl`, `sanitizeBlock`, `validateAndSanitizeDeck`, `isSvgStyleSafe`) sits at
`src/parts/part-imports.jsx:451-1177` — buried mid-file in a ~48K-token file. Its
regression suite is at `src/parts/part-uitest.jsx:1361-1643` inside a 62,886-token
file, and the Python security assertions at `tests/test_vela.py:123-962` inside a
70,344-token file. `/security-review` and reviewer subagents cannot hold any of the
three whole, and mid-file is exactly where positional bias ("lost in the middle")
degrades attention most.

### Three hardcoded part lists — two are stale

`PART_ORDER` is duplicated across three files. Only one is correct:

| Location | Parts listed | `part-pptx.jsx`? |
|---|---:|---|
| `tools/vela-dev/scripts/concat.py:21` | 14 | ✅ present |
| `tools/vela-dev/scripts/lint.py:15` | 13 | ❌ **missing** |
| `tests/test_vela.py:53` | 13 | ❌ **missing** |

Consequences: `part-pptx.jsx` (1187 lines) is never linted for copyright header,
conflict markers, brace balance, or cross-part duplicate declarations, and the unit
test that asserts "all part-files present" silently ignores it. The test's own comment
reads `# 1. All 11 part-files exist` while the list holds 13 — the comment drifted too.

**And `lint.py` is wired into nothing** — absent from every `.github/workflows/*.yml`
and from `tools/vela-dev/scripts/ci-local.sh`. It is dead tooling, which is why the
drift went unnoticed.

### External guidance

Practitioner consensus is **150–500 lines of real code per source file**, split at
logical boundaries rather than arbitrary counts. The constraint that actually binds
here is the 25K-token read window, so the target below is in tokens, with lines as a
proxy.

Sources: [Right-Sizing Your Python Files: The 150–500 Line Sweet Spot](https://medium.com/@eamonn.faherty_58176/right-sizing-your-python-files-the-150-500-line-sweet-spot-for-ai-code-editors-340d550dcea4) ·
[Claude Code Read tool 25k token limit (issue #15687)](https://github.com/anthropics/claude-code/issues/15687) ·
[Context Rot: Why LLMs Degrade as Context Grows](https://www.morphllm.com/context-rot) ·
[Context engineering for large codebases](https://packmind.com/context-engineering-ai-coding/context-engineering-large-codebases/) ·
[The New Rules of Context Engineering for Claude 5](https://www.developersdigest.tech/blog/context-engineering-claude-5-new-rules-2026)

### Outcome

Every source, test, and tooling file readable in a single `Read` call. No runtime
behaviour change, and the shipped `skills/vela-slides/app/vela.jsx` comes out
**byte-identical**.

---

## Target

- **Hard ceiling: ≤20K tokens per file** — a 20% margin under the 25K cap.
- **Floor: ~250 lines.** Do not shard below this; extra files cost grep hops.
- Cut at the existing `// ━━━` / `// ──` banners. They already mark clean seams.
- No bundler. The ~10 ms Python-stdlib concat stays as it is.

**Every cut point below has been size-verified.** Each chunk's measured token count is
listed; all land under 20K.

---

## Work

### 1. Fix the build-tooling foundation first

- **Single-source the part list.** Create `src/parts/MANIFEST.txt` — one part filename
  per line, dependency order, `#` comments allowed. `concat.py`, `lint.py`, **and
  `tests/test_vela.py`** all read it; delete all three hardcoded lists
  (`concat.py:21`, `lint.py:15`, `test_vela.py:53`). Drop the stale
  `# 1. All 11 part-files exist` comment.
- **Make `lint.py` reject unknown parts.** Any `src/parts/part-*.jsx` not in the
  manifest is an error, not a silent skip — otherwise a split file that nobody wires up
  vanishes from the build and from lint.
- **Wire `lint.py --parts src/parts` into `.github/workflows/ci.yml` and
  `tools/vela-dev/scripts/ci-local.sh`**, next to the existing Template Sync step.
- **Add a size guard** to `lint.py`: warn over 700 lines, fail over 900.

### 2. Extract the PDF font blobs

`src/parts/part-pdf.jsx:2148-2156` holds `COMPRESSED_FONTS` — six base64 TTF blobs on
single lines of 35–51 KB each, **242 KB of the file's 413 KB**. They are the runtime
offline fallback (`FONT_CDN_URLS` is the network path), so they must still ship.

Move the object verbatim to `src/parts/part-pdf-fonts.jsx`, registered immediately
before `part-pdf.jsx`. Only two reference sites, both in `loadFonts()` at
`part-pdf.jsx:2887-2888`, both already guarded by `typeof COMPRESSED_FONTS !== "undefined"`.
This is what makes the file openable at all.

### 3. Split the over-cap part-files

Mechanical each time: cut at the listed lines, move blocks verbatim (no reformatting,
renaming, or reordering within a chunk), add the new names to `MANIFEST.txt` in the
original relative order, rebuild, diff.

**Ordering constraint:** top-level `const`/`let` are TDZ-bound, so cross-part relative
order must be preserved exactly. Keeping manifest order identical to the current
concatenation order satisfies this automatically.

Notes on the two non-obvious ones:

- **`part-imports.jsx`** — the 425/1035 pair isolates the security surface into two
  self-contained readable files (`part-sanitize`, `part-sanitize-deck`). That is the
  single highest-value outcome of this sprint for review quality.
- **`part-blocks.jsx`** — the cut at **952** splits `RenderBlock`'s 27-case switch:
  simple/text cases (767–951) stay in `RenderBlock`; the data/diagram cases
  (952–1514: flow, table, progress, steps, tag-group, timeline, comparison, funnel,
  cycle, number-row, matrix, checklist) move to a `RenderDataBlock` component reached
  from the switch's `default:`. **Verified safe: lines 952–1514 contain no hook calls**,
  so extracting them as a plain component cannot change hook order. The shared context
  the preamble computes (`block`, `st`, `SIZES`, `cls`, `canEdit`, `textEditable`,
  `_pin`) passes through as props — `_pin` is used at 10 call sites in that range. This
  follows the existing `CodeBlock` / `CalloutBlock` extraction precedent at lines 725
  and 746. Leaving `RenderBlock` whole is **not** an option: at 25,597 tokens it is over
  the hard read cap on its own.

### 4. The two monolithic components

The only items needing real code movement rather than file cuts, and the only places
behaviour can regress.

- **`SlidePanel`** — `part-slides.jsx:1342-2564`, 1223 lines / **40,028 tokens**, one
  component with no extractable top-level children. Hoist the prompt-driven AI action
  handlers to module scope as plain functions taking `(state, dispatch, …)`: Quick Edit
  (2003), Block-Targeted Edit (2032), Generate New Slide (2060), Alternatives (2191).
  Then the browser-integration effects: back-button (1911), Fullscreen API sync (1921),
  scroll-wheel nav (1944).
- **`App`** — `part-app.jsx:1096-2014`, `export default function App()`, 919 lines /
  **29,646 tokens**. Same treatment: hoist keyboard handlers, storage effects, and
  modal routing to module scope.

Both are behaviour-preserving hoists. Guard them with the full test suite **and** the
headless UI battery, not the byte-identical check — hoisting legitimately changes the
emitted source, so `vela.jsx` will differ for these two.
